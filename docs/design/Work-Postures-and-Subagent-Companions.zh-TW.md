# Agent Pets 工作姿態與子代理跟班設計提案

2026-11-18，以 Agent Pets 1.14.4 為基準。本文供產品、設計、adapter 開發與測試共同使用。標為「現況」的內容已對照本機程式碼；畫面、資料流與驗收條件是待評估的提案。上游 hook 的父子歸屬有文件依據，實際安裝版本的派工、停止與中斷行為仍待採樣。

## 1. 產品決策

**先讓人看懂一隻寵物正在做什麼，再顯示這次任務有哪些幫手。** 工作姿態可利用既有工具事件，先回答「它在找資料、改檔，還是跑命令？」。跟班需要另一項能力：把子代理的開始與停止可靠地歸給畫面上的那個工作階段。分開交付，才能在父子資料不完整的平台先提供有用的工作姿態。

| 階段 | 使用者得到什麼 | 進入下一階段的依據 |
| --- | --- | --- |
| 一．主寵工作姿態 | 主寵身旁出現文件、鉛筆或終端；舊寵物包也可顯示 | 盲看能辨識三類活動；快速切換仍可看懂，權限提示不受延遲。 |
| 二．跟班與在場數 | 先以 Codex 為候選來源，顯示一層子代理、在場數與可展開的工作階段明細 | 真實事件可重建父子歸屬；兩個平行聊天不串線，重送、異常離場皆有可預期結果。 |
| 三．每隻跟班的姿態 | 能辨別子代理活動的來源可分別顯示讀取、編輯或執行 | 工具事件有可核對的子代理身分，同時三個執行者仍能各自顯示正確活動。 |

例如一個聊天先後派出六位研究員，第一批三位在場、一位交回結果、新的一位加入。在場數應是 **3 → 2 → 3**；「曾派出六位」屬於整次任務的歷程。若另一個聊天也在同一專案工作，其活動由自己的工作階段呈現。桌面以當下在場者為主，第一版的明細也只呈現目前可確認的名單。視覺參考採自 ai-pet 的工作場景與「最多三隻，其餘用數量顯示」行為。[工作場景與跟班示例](https://github.com/thgoas/ai-pet#what-the-assistants-up-to)

### 子代理跟班開關

第二階段在「設定 → 寵物」的「多寵物」旁新增獨立開關 **子代理跟班**。建議說明文字為「在主寵旁顯示這次任務的幫手，並在工作階段中查看名單。」這是整個 App 共用的偏好，切換後立即套用到寵物視窗和面板，重啟後保留使用者的選擇。主寵的讀取、編輯與執行姿態在四種組合下都依工作事件顯示。

| 多寵物 | 子代理跟班 | 桌面與面板 |
| --- | --- | --- |
| 關 | 關 | 單一主寵顯示代表聊天的工作姿態；面板省略跟班區塊。 |
| 關 | 開 | 同一隻主寵可帶目前代表聊天的跟班；面板能查看各聊天自己的名單。 |
| 開 | 關 | 多個工具家族作用時各有一隻主寵；面板省略跟班區塊。 |
| 開 | 開 | 每隻主寵只帶該家族代表聊天的跟班；只有一個家族作用時仍可顯示其跟班。 |

**關閉**會收起跟班、數量、名單與相關讀屏提示，主程序停止追蹤並清除跟班暫存。已派出的子代理繼續在來源工具執行。**重新開啟**時，若來源能提供完整的在場名單，便直接還原；僅能收到後續事件時，面板先顯示「資料不足」，收到新事件後顯示「已觀測 N 位」。來源尚未支援時顯示「此來源尚未支援」。新安裝及升級後尚無此偏好的使用者，其預設值留待第二階段決定。

## 3. 工作姿態的判定與畫面

第一階段表達的是「這個工作階段觀察到的工具活動」。Claude 前景子代理可能共用父 `session_id`，1.14.4 的一般事件沒有保留子代理身分，因此道具不能用來認定主代理親自執行。若要把道具分給個別執行者，需通過第三階段的歸屬驗證。[既有 hook 取捨](../phase-reports/phase-hooks-reliability.md)

僅在目前代表工作階段處於 `tool-running` 時分類。每個來源列出經該 adapter 驗證的完整工具名稱及別名，映射到以下三類。這些分類屬於畫面層的描述，Agent 狀態仍沿用既有 registry。名稱相似的第三方工具先回到一般姿態。

| 類別 | 可採用的證據 | 寵物怎麼呈現 | 可以對使用者說什麼 |
| --- | --- | --- | --- |
| 讀取 | 來源可辨識的讀檔、列舉或搜尋工具 | 身旁有打開的文件；有動態時低頻翻頁 | 「正在查找或閱讀資料」 |
| 編輯 | 來源可辨識的寫檔或套用補丁工具 | 文件旁出現鉛筆；有動態時寫一筆 | 「正在編輯」；成功與失敗等工具回報。 |
| 執行 | 來源可辨識的 shell／程序執行工具 | 身旁出現小終端；靜止畫格仍看得出外形 | 「正在執行命令」；通用 shell 可能在列目錄、建置或測試。 |
| 一般工作 | 缺名稱、未知名稱、缺少適用的對映 | 沿用原工作姿態 | 使用既有工作狀態文字。 |

**道具配置。** 第一版由主程式提供三個小道具，固定在精靈旁的可用位置。這適用於手腳位置不同、甚至沒有手的角色。素材作者後續可選擇提供完整姿態；是否擴充素材格式，留待確認道具的辨識度與作者需求之後決定。

**切換節奏。** 同一個 session 連續讀取時，保留已打開的文件。同類工具結束與下一個同類工具開始若非常接近，可延後收起道具以減少閃爍；短暫保留僅作動畫收尾，文字狀態按事件更新。切換代表 session、收到錯誤、等待輸入／權限、工作結束或斷線時，立即撤下舊道具並取消待執行的計時器。原型可比較「立即收起」與「短暫收起延遲」兩組錄影，選擇不易誤讀的節奏。

## 4. 桌面與工作階段明細

下表的跟班呈現以「子代理跟班」已開啟為前提。

| 情境 | 工作姿態 | 子代理跟班 |
| --- | --- | --- |
| 一般單寵 | 依主寵對應的工作階段顯示道具 | 顯示最多三隻與超額數。例如五位為三隻加 `+2`；沒有可顯示的跟班時收回空間；使用者可到明細區分「已確認 0 位」「資料不足」與「此來源尚未支援」。 |
| 多家族同時工作 | 每個家族讀自己的代表 session；同家族代表改變時同步更換 | 各歸各的主寵；空間不足時先縮成「幫手 3」，保留原本的狀態、額度與等待提示。 |
| Mini／邊緣收合 | Mini 優先保留原狀態圖示；邊緣把手沿用重要狀態與完成標記 | Mini 有空間才顯示數量；邊緣收合先省略跟班，展開可看完整資訊。 |
| 等待權限、錯誤、勿擾 | 遵守既有重要提示與勿擾規則；收起工作道具與裝飾動作 | 停止入場、離場動效；靜音期間仍可更新已觀測名單。回復顯示時用當下快照。 |
| 減少動態／高對比 | 用形狀區分文件、鉛筆、終端，提供本地化文字；道具可完全靜止 | 固定位置和數量文字替代移動。讀屏摘要例如「Codex，正在執行命令，2 位幫手」。 |

本文的「代表工作階段」是桌寵當下對應的聊天；「在場」指來源資料能確認仍在這次派工中的幫手，含已確認正在等待輸入的幫手。桌面數字只計該聊天的一層直接幫手，每位計一次。主寵、其他聊天、孫層代理與已確認離場者都不計入。`+2` 表示另有兩位已確認在場者未能畫出；讀屏與面板報告總數，例如「5 位幫手，畫面顯示 3 位」。

使用者沿原有點寵物或鍵盤開面板的操作，在 Sessions 展開對應工作階段，看到「子代理（2）」與每位目前可確認的狀態。建議用穩定的「幫手 1」「幫手 2」作缺省名稱，保留在場期間的編號與位置。來源只提供角色類別（例如 `Explore`）時可顯示「幫手 1 · Explore」，它是角色類別。若來源另有可驗證的顯示名稱，經長度與顯示字元檢查後才能顯示。子代理需要回應時，僅以可歸屬的真實等待事件標記；操作入口仍由現有工作階段與權限流程提供。

寵物與道具同屬內容層，裝飾不攔截滑鼠，跟班共用主寵視窗。面板入口沿用既有按鈕、焦點與主題元件。讀屏可在使用者選取的工作階段查詢摘要；同類工具切換不反覆播報。以亮暗桌布、100／125／150% 縮放、螢幕邊界與多螢幕驗證溢位、點擊穿透及拖曳。[桌寵視圖](../../src/components/DesktopPet.vue) · [既有宣讀區域](../../src/components/desktop-pet/PetBubbleStack.vue) · [Liquid Glass 規則](../../.agents/skills/pet-skill/references/liquid-glass.md)

## 5. 來源可用性與真實派工採樣

| 來源 | 已知證據 | 啟用門檻 |
| --- | --- | --- |
| Codex | 官方說明子代理 hook 的共通 `session_id` 為父 session；`SubagentStart`、`SubagentStop` 都列出 `agent_id`、`agent_type` 與 `turn_id`。`turn_id` 表示作用中的 Codex 回合；同一回合可派出多位幫手。現有 Agent Pets hook 需增加訂閱。[Codex hook 規格](https://learn.chatgpt.com/docs/hooks#common-input-fields) | 第一個候選。分別記錄實際測試的 CLI／Desktop 版本及入口，確認兩個主聊天同時派工時能分組、相同幫手恢復後能區分執行輪次。 |
| Claude Code | `SubagentStart` 有 `session_id`、`agent_id`、`agent_type`；`SubagentStop` 也可能來自 Claude 內部功能。[開始事件](https://code.claude.com/docs/en/hooks#subagentstart) · [停止事件](https://code.claude.com/docs/en/hooks#subagentstop) | 用成對且可歸屬的外部派工先驗證。孤立的 stop、其他 hook 使子代理繼續執行、CLI／Desktop 重複來源均需測試。 |
| OpenCode | 目前 Agent Pets 接受 `sessionID` 與工具活動。V1 SDK 的 `session.children` 可列出子 session；清單本身無法證明哪些正在執行，仍須核對已安裝插件版本實際提供的開始與停止訊號。[目前插件](../../electron/setup.ts) · [OpenCode SDK](https://opencode.ai/v1/docs/sdk/) | 先驗證 session 與工具事件隔離；親子證據未齊全前只提供能可靠辨識的工作姿態。 |

採樣從一次可核對的操作開始：同一資料夾開 A、B 兩個聊天；A 派兩位，B 獨立工作；讓一位自然停止、一位被中斷，再恢復或重新派工。另測桌寵中途才啟動。記下操作序列、產品版本、hook 是否已安裝並受信任、來源 ID 的匿名代號、收到的事件順序與缺口。用同一組代號核對觀察紀錄和桌寵名單。子代理開始／停止可識別，並不自動代表其一般工具事件也含執行者身分；後者單獨驗證。

## 6. 事件契約與生命週期提案

建議在第一階段沿用既有狀態事件。第二階段增加可辨別的「子代理生命週期」事件種類，在主程序入口完成執行期驗證後，交給獨立的記憶體名單。既有工作狀態、歷史、XP、成就與通知消費者繼續只處理其原有事件。欄位名稱以下用來說明語意，實作時再與 adapter 契約對齊。

| 資料 | 用途與約束 |
| --- | --- |
| 來源、父 session ID、子代理 ID | 三者共同決定歸屬。驗證來源、型別、非空與長度；在 adapter 檢查原始父、子 ID；現行 hook 會把缺失的 session ID 補為 `unknown`，這個替代值不能拿來建立親子關係。專案路徑、相近時間、相同模型皆不足以配對。 |
| 開始／停止 | 開始表示已觀察到在場。來源若已確認終止，可移出該輪；若 stop hook 尚可能被其他 hook 要求繼續，標為「停止待確認」，等後續活動或來源快照再校正名單。成功、取消或失敗須另有證據。 |
| 執行輪次、來源序號或事件 ID（來源提供時） | 事件 ID 可去除同一筆重送，但本身沒有先後順序。來源序號僅在其保證的範圍內比較；輪次識別需實證可區分恢復前後。來源和接收端的時間都不能單獨判斷舊輪復活。 |
| 可選角色名稱、活動類別 | 角色類別、顯示名稱只供展示。同名或同模型的兩位仍依各自識別計數。活動類別僅接受可歸到該 child 的事件；無證據就顯示一般工作。 |

| 收到的序列或異常 | 名單與顯示結果 |
| --- | --- |
| 同一輪 start、start、stop、stop | 來源已確認終止時，第一次開始加入一次，第一次有效停止移出一次；後續重送不增加人數，也不多發一次離場提示。 |
| 同一輪 stop 先到，較舊的 start 後到 | 對可區分的輪次短暫保留停止記錄，忽略遲到的舊開始。孤立 stop 不建立可見項目。 |
| 已停止的 child 再啟動 | 有新輪次證據才重建。無法區分重送或恢復時保持未知，等待新的可驗證訊號；這項能力需在來源矩陣註明。 |
| 工具事件先於配對資料、或同 ID 出現在不同父 session | 不憑工具事件創造跟班；以完整父子識別隔離。主寵工具事件也不能替子代理更新道具。 |
| 父回合停止／父 session 結束 | 父回合 `Stop` 可早於背景幫手結束，維持獨立跟班名單；晚到的子事件只更新名單，不把已結束的父回合改回工作中。確認父 session 已結束時收回桌面跟班，遲到事件不得重新建立父 session。 |
| 連線中斷、中途啟動或桌寵重啟 | 若有可核對的在場快照，以快照重建；只有新事件時標示「已觀測 N 位／部分資料」，零筆在面板顯示「資料不足」。「共 0 位」須有完整資料才可顯示。 |
| 大量跟班、舊事件堆積 | 對每個父 session、全域名單與短期停止記錄設上限和清理期限；上限值用實測峰值決定。若追蹤不完整，介面標示「部分資料」，避免以截斷值冒充總數。 |

主程序維護當下快照。視窗先訂閱並暫存更新，再讀取帶修訂號的快照，套用比快照新的更新；修訂號斷層就重取快照。這也涵蓋讀快照期間恰好有子代理離場的情況。關閉跟班時主程序停止累計並清空暫存；重新啟用時依中途啟動規則標記完整度。原型僅保留在場資訊，不保存跨日派工歷史。新增 hook 採用現有安全合併方式，升級、重複安裝及移除只處理 Agent Pets 自己的項目。Codex 增加新 hook 可能要求重新審核，先在隔離設定驗證支援版本；未驗證舊版解析新事件的行為前，沿用既有設定。觀測 hook 的輸出遵循來源的中性回覆契約，避免加入提示內容、阻止停止或要求繼續。[先前的舊版相容性與信任紀錄](../phase-reports/phase-hooks-reliability.md) · [設定合併實作](../../electron/hook-config.ts)

**兩種快照的證據不同。** 來源提供且能說明執行狀態的快照才可補回漏接的派工；主程序給 renderer 的快照只同步桌寵已知資料，必須一併傳遞完整度。僅收到零散 hook、無法發現漏件的來源使用「已觀測 N 位」；有停止待確認者在明細另列。例如一位仍在場、另一位停止待確認，顯示「已確認 1 位，另 1 位待確認」。

**資料與權限邊界。** 在 adapter 端挑出必要欄位；即使來源 payload 附上提示詞、最後回覆、命令參數、工作路徑或 transcript 路徑，跟班功能也無需轉送或保存。主程序驗證 loopback 請求，renderer 只取得顯示快照。跟班事件不觸發 XP、權限決定或專案寵物重新路由；既有 Presentation MCP 保持狀態、反應與發言三種用途。[專案架構與權限模型](../architecture/Desktop-Pet-Architecture-v2-Feature-Roadmap.zh-TW.md)

**同一情境的跨角色驗收。** 以下為事先寫下的預期結果，供設計、adapter 與 QA 使用同一條重播資料比對。A、B 代表同一家族的兩個獨立聊天，a1、a2 代表 A 的直接幫手。前四步假設來源有足夠證據確認在場與終止。

| 操作與事件 | 一般使用者與讀屏應得到的資訊 | 開發與 QA 的檢查點 |
| --- | --- | --- |
| A 較早開始讀檔，B 稍後開始編輯；兩者皆工作中 | 主寵維持 A 的文件道具。 | 較新的 B 工具事件不能替 A 換成鉛筆。 |

| B 開始等待權限，成為代表工作階段 | 桌面改顯示 B 的權限提示。打開 A 的明細仍看得到兩位幫手。 | 切換代表只改桌面顯示；A 的名單與 B 的權限流程獨立。 |
| A 的主回合先停止，稍後 a1 有可確認的終止事件 | A 的明細剩 1 位。主回合狀態不因 a1 離場而回到工作中。 | 子事件僅減少 A 的名單，不產生第二次父回合完成、XP 或通知。 |

每一階段交付一份去識別的事件序列與預期畫面、一段真實 Electron 錄影、測試來源和版本清單，以及確認過的平台與限制。工作姿態另比較既有畫面與候選畫面辨識「讀、改、跑」的正確率、所需時間及漏看等待提示的次數。以現有動作與事件測試為起點；分類和重播測試能證明對映，真實桌面錄影才能確認使用者看見的動作。[動作測試](../../tests/pet-motion-plan.test.mts) · [hook 對映測試](../../tests/agent-hook-mapping.test.mts) · [工作階段視圖測試](../../tests/session-view.test.mts) · [家族代表與優先序測試](../../tests/session-attention.test.mts)
