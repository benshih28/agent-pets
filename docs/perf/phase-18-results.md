# Phase 18 效能結果

量測日期：2026-10-26。基準數據取自 [`phase-18-baseline.md`](./phase-18-baseline.md)，本次由 `pnpm bench` 產生。微基準固定亂數種子，暖機 3 次後量測 30 次；冷啟動量 5 次。正改善率代表中位數較快，負值代表較慢。所有輸入與暫存資料均為合成資料。

## 基準與本次結果

| 項目 | 複雜度（基準 → 本次） | 基準中位數／p95（ms） | 本次中位數／p95（ms） | 中位數改善率 | 結果說明 |
| --- | --- | ---: | ---: | ---: | --- |
| 本機用量首次掃描（50 個 JSONL、合計 200 MiB；掃描上限 64 MiB） | O(B+F) → O(B+F) | 114.655／123.033 | 52.759／56.338 | +54.0% | 首次掃描仍需讀取可掃描資料；複雜度不變，實測時間下降。 |
| 本機用量追加 1 MiB 後掃描 | O(B+F) → O(F+ΔB) | 110.095／115.372 | 50.146／52.811 | +54.5% | 使用檔案識別資訊與 byte offset 續讀；未改變輸出格式。 |
| Agent 狀態事件（1,000 個 session、10,000 筆事件） | 最壞 O(E×S) → 平均 O(E) | 84.608／102.619 | 6.606／8.961 | +92.2% | Map 索引避免新增 session 時逐次掃描；同次量測中的舊路徑為 115.460／170.173 ms。 |
| 泡泡仲裁（10,000 組候選） | O(1) → O(1) | 0.202／0.331 | 0.281／0.449 | −39.1% | 候選類別數固定，量測後不需優化；本次未改仲裁演算法，總耗時仍低於 0.5 ms。 |
| 插件 feed enqueue/dequeue（10,000 筆） | O(1)（佇列深度固定 8）→ O(1)（固定優先桶） | 80.165／92.878 | 155.836／165.807 | −94.4% | 新路徑加入 Map 去重、優先桶與佇列 TTL 管理；CPU 時間增加，換得穩定排序與去重。此量測未顯示吞吐改善。 |
| Plugin net 限流（每秒 10,000 次） | O(r) → 攤銷 O(1) | 17.540／20.825 | 17.325／19.456 | +1.2% | 環狀視窗依序清除到期項目；本次中位數小幅下降。 |
| Feed 限流（每秒 10,000 次） | O(r) → 攤銷 O(1) | 10.613／10.925 | 14.298／15.272 | −34.7% | 複雜度改善，但在此工作量下固定容量檢查與多層狀態管理的常數成本較高。 |
| Badge 限流（每秒 10,000 次） | O(1) → O(1) | 6.524／6.825 | 10.279／12.754 | −57.6% | 既有行為已是每插件記錄最近時間的 O(1) 路徑；本 Phase 未以漸近複雜度為由宣稱改善，差異視為微基準變動。 |
| eventSource 限流（每秒 10,000 次） | O(r+s) → 攤銷 O(1) 限流檢查＋有界 session 更新 | 46.230／47.664 | 53.147／54.663 | −15.0% | ring buffer 避免常態時間戳篩選；額外視窗與 session 驗證使此工作負載的實測時間增加。 |
| Command 限流（每秒 10,000 次） | O(1) → O(1) | 3.289／3.771 | 4.776／5.280 | −45.2% | 每指令仍只讀寫最近呼叫時間；複雜度未變，本次實測較慢，不宣稱效能提升。 |
| History 七日統計（100,000 筆） | O(log N+k) → O(log N+k) | 430.839／470.834 | 450.488／474.607 | −4.6% | 新增涵蓋索引後查詢計畫不再回表；此工作負載沒有量到時間改善。 |
| History 專案篩選（100,000 筆） | O(log N+m) → O(log N+m) | 0.167／0.328 | 0.273／0.891 | −63.5% | 複雜度相同且結果集很小；次毫秒差距對排程與快取狀態敏感，本次不宣稱改善。 |
| 隔離 Electron 冷啟動（5 次） | 不適用（程序與視窗初始化） | 2,341.864／2,411.462 | 3,254.217／3,452.691 | −39.0% | 本次冷啟動較慢；單靠微基準不能定位原因，主程序 bundle 增加 4.49% 是可能因素，仍需 profiler 確認。列為待決效能風險。 |

`B` 為輸入位元組數、`F` 為檔案數、`ΔB` 為追加位元組數、`E` 為事件數、`S` 為 session 數、`r` 為視窗內時間戳數、`N` 為 History 資料列數、`k`／`m` 為符合篩選的資料列數。

## 固定亂數種子等價性驗證

- 用量增量解析與完整解析比對 1,000 個固定種子檔案，涵蓋 UTF-8 byte boundary。
- Agent session `Map` 索引與舊 eviction 實作比對 1,000 組事件串流；feed 分桶佇列與參考佇列比對 1,000 組操作案例。
- 共用 sliding-window limiter 與舊 array-filter 規則比對 1,000 組操作序列；History 涵蓋索引啟用／停用分別執行 1,000 組固定種子查詢並比對結果。
- latest-value 與 ordered-batch broadcast coalescer 各比對 1,000 組固定種子事件批次，確認最終投影與原始事件順序。
- Bubble、Badge 與 Command 的複雜度沒有改變；報告保留慢於基準的數字，未將其描述為優化成果。

## 結論與限制

- 明確的時間改善出現在增量用量掃描與 Agent session 索引；Agent 事件中位數降低 92.2%。Plugin net 限流只有 1.2% 中位數改善，幅度接近量測變動。
- Feed queue、Feed/eventSource 限流與冷啟動在本次量測變慢。Feed queue 的固定優先桶與去重 bookkeeping 有額外 CPU 成本；限流器的漸近複雜度改善沒有在每個 controller 的這組微基準中轉成較低時間。冷啟動原因尚未經 profiler 證實。
- 泡泡仲裁、Badge、Command 與 History 專案篩選未量到改善；微基準時間皆低於 13 ms，History 專案篩選低於 1 ms。依「不做沒必要的微優化」原則保留可讀性與既有行為。
- Benchmark 使用固定合成資料與同一執行工具；冷啟動只有 5 個樣本。實際硬體、檔案快取與其他程序會影響結果，不能據此推論所有裝置的使用者體感。
